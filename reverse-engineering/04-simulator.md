# 04. Симулятор дежурств

Движок: `src/sim/engine.ts` (~1260 строк). Он **детерминированный** (никакой случайности), чистый (принимает граф и состояние, возвращает новое состояние и метрики) и работает одинаково в браузере и на сервере (плейтест ИИ-сценариев). Тесты: `src/sim/engine.test.ts`.

## Публичный API движка

| Функция | Назначение |
|---|---|
| `createState(graph)` | Начальное состояние `SimState` для графа |
| `step(graph, state, { scenario?, manualLoad? })` | Один тик = одна минута. Возвращает `{ result: TickResult, state }` |
| `onGraphChange(prev, next, state)` | Игрок поменял граф: новые узлы, новые инстансы и смена размера уходят в прогрев |
| `staticAnalysis(graph)` | Стоимость в месяц, единые точки отказа (SPOF), предупреждения |
| `blockSpecs`, `sizeMult` | Справочник блоков и множители размеров |

Игровой цикл `src/sim/useSimulation.ts` держит граф, состояние, историю тиков, алерты и действия игрока; скорость ×1/×2/×4 = 1000/500/250 мс на тик. Состояния игры: `briefing → running ⇄ paused → won | lost`.

## Модель

### Нагрузка

Трафик делится на три класса, в rps: `read`, `write`, `static`. В сценарии нагрузка = `baseLoad × trafficCurve(t) × trafficMult`, где `trafficCurve` кусочно-линейная, а `trafficMult` меняют события `traffic`. В песочнице нагрузку задаёт игрок ползунками (`manualLoad`, по умолчанию 300/60/50). DDoS добавляет «мусорные» чтения.

### Обход графа

1. Граф обходится в топологическом порядке DFS от узлов `client`; обратные рёбра (циклы) отбрасываются.
2. Каждый узел получает нагрузку от родителей, считает загрузку и раздаёт трафик детям по правилам своего типа.
3. Отброшенное узлом (перегруз, rate limit) дальше по цепочке не идёт.

### Загрузка, задержка, ошибки

Для каждого узла `ρ = used / capacity`, где `capacity = spec.capacity × sizeMult × работающие инстансы`.

- `ρ < 1`: задержка `base × slow × min(30, 1 / max(0.05, 1 − ρ))` (очередь M/M/1 с ограничением хвоста 30×), ошибок нет.
- `ρ ≥ 1`: задержка = таймаут 5000 мс, доля ошибок `1 − 1/ρ` (всё сверх ёмкости отбрасывается).
- Узел лежит: весь входящий трафик превращается в ошибки, задержка 5000 мс.

Сквозной p99 = `2.5 × средневзвешенная задержка синхронных путей` (взвешивание по долям трафика: при попадании в кэш до БД доходит меньше). Ошибка пользователя считается только по живому трафику, без DDoS-мусора.

### Деньги

Стоимость в месяц = сумма по узлам `spec.cost × sizeMult.cost × инстансы` плюс оплата за запросы (`usdPer1kReq`, сейчас только у `llm`) при текущем rps.

Размеры дают убывающую отдачу:

| Размер | Ёмкость | Цена |
|---|---|---|
| S | ×1 | ×1 |
| M | ×2 | ×2.2 |
| L | ×4 | ×5 |
| XL | ×8 | ×11 |

### Прогрев

Новый узел, добавленный инстанс или смена размера (это рестарт всех инстансов) не дают ёмкости `warmupTicks` минут. Перк «Быстрый деплой» пропускает прогрев одного изменения.

## Маршрутизация в сервисе

`service`/`worker` отправляют трафик так:

- **Чтения:** 30% в `search` (если есть), остальное через `redis` (промахи в БД), иначе прямо в `postgres`/`replica`.
- **Записи:** через `queue`/`kafka` (асинхронно, быстрый ack), иначе напрямую в `postgres`. Плюс синхронный вызов `external` на каждую запись (платёж).
- **LLM-конвейер:** `semcache` → при промахе `vectordb` + `llm`. Агент делает 3 вызова LLM на задачу (событие `loop` увеличивает, knob `maxSteps` ограничивает).
- **Аналитика:** событие на каждый запрос в `clickhouse`, асинхронно.
- **Статика:** в `s3`, иначе сервис отдаёт сам (дорого).
- Вызовы других `service` синхронные и получают весь трафик.

## Настройки (Knobs)

`src/sim/knobs.ts`. Значения по умолчанию подставляются, если knob не задан.

| Knob | Блоки | По умолчанию | Эффект |
|---|---|---|---|
| `retries` | service, worker | 0 | Множитель нагрузки `1 + e + e² + …`; retry storm при перегрузе |
| `timeoutMs` | service, worker | 2000 | Обрезает ожидание; при медленной зависимости доля таймаутов |
| `threads` | service, worker | 200 | Пул потоков: ёмкость упирается в `threads / hold-time` |
| `dbPool` | service, worker | 20 | Соединений на инстанс; нехватка = pool exhaustion |
| `autoscale`, `autoscaleMax` | service, worker | off, 10 | Автоскейлер по CPU или по лагу очереди |
| `rebalance` | worker | eager | Eager-ребаланс Kafka останавливает всю группу; cooperative нет |
| `maxConnections` | postgres | 500 | После 300 соединений БД замедляется; сверх лимита «too many connections» |
| `indexed` | postgres | true | Без индекса чтение стоит 8 единиц ёмкости |
| `ttlSec` | redis / cdn / lb | 300 / 3600 / 0 | Hit ratio масштабируется `ttl/(ttl+30)` |
| `evictionPolicy` | redis | allkeys-lru | `noeviction`: память забита, hit падает до 50% |
| `partitions`, `offsetReset` | kafka | 12, earliest | Параллелизм консьюмеров; `latest` теряет бэклог после простоя |

В режиме «Наследство» (`configOnly`) топология и размеры заморожены, а инспектор (`src/sim/config.ts`) показывает фрагмент реального конфига (nginx, postgresql.conf, redis.conf, …) с подсвеченными строками.

## События сценария

`ScenarioEvent { at, kind, target?, value?, duration?, message }`. `target` это id узла или тип блока (берётся первый узел этого типа).

| `kind` | Что происходит |
|---|---|
| `traffic` | Множитель нагрузки = `value` с этого момента |
| `kill` | Узел лежит `duration` минут или навсегда; для postgres запускается failover |
| `killOne` | Умирает один инстанс |
| `slow` | Задержка × `value` на `duration` |
| `cacheFlush` | Hit ratio падает до 0 и линейно восстанавливается за `duration` |
| `ddos` | `value` rps мусорных чтений |
| `zoneDown` | Падают все узлы с `zone === target` (кроме клиентов и внешних) |
| `stall` | Воркер «живой мертвец»: жив, но ничего не разбирает |
| `restartLoop` | Инстанс воркера перезапускается каждые `value` тиков (утечка памяти) → ребалансы |
| `loop` | Агент делает `value` вызовов LLM на задачу |
| `enqueue` | `value` сообщений разом в очередь (бэкфилл, переиндексация) |
| `degrade` | Ёмкость ÷ `value` (плохая регулярка, шумный сосед) |

## SLO, здоровье и исход

Тик нарушает SLO, если выполнено хоть одно:

- `p99Ms > slo.p99Ms` или `errorRate > slo.errorRate`;
- потеряно сообщений больше `slo.maxLost`;
- лаг любой очереди/Kafka больше `slo.maxLagSec`;
- стоимость больше `slo.maxCostPerMonth`.

Здоровье = `100 × (1 − нарушенных_минут / errorBudgetMin)`. При 0 игра проиграна, при доживании до `durationMin` выиграна. Перк «Кофе-брейк» на 3 минуты замораживает сгорание бюджета.

## Статический анализ

`staticAnalysis` вне тиков:

- **SPOF:** узлы типов `lb, gateway, service, postgres, redis, queue, kafka, search` в одном инстансе без «соседа» того же типа под тем же родителем (для postgres соседом считается реплика).
- **Предупреждения:** блок не подключён к клиенту; сервис ходит в Postgres без кэша; несколько инстансов сервиса без балансировщика; очередь без воркеров; Kafka меньше чем на 3 брокерах; реплика без Postgres.

## Гарантии через тесты

`src/sim/engine.test.ts` проверяет **механику модели** на синтетических графах: убывающую отдачу размеров, кэш и `cacheFlush`, реплики и лаг, очередь, перегруз и rate limit, отказы и failover, прогрев, детерминизм, циклы, статический анализ, DDoS и все knobs (retry storm, таймауты, индекс, пул vs `max_connections`, партиции Kafka, TTL, `noeviction`, автоскейлер, eager-ребаланс, stall, `offsetReset`, `zoneDown`).

**Важно:** README утверждает, что каждый сценарий (обычный, «Наследство», хардкор) проверен ботом на проходимость. Таких тестов в репозитории **нет**: `engine.test.ts` не импортирует ни одного файла сценариев. Проходимость сценариев сейчас ничем автоматически не гарантирована (см. [08-findings.md](08-findings.md)). Для Blue Team, наоборот, такие тесты есть: эталонный набор каждого уровня блокирует ≥ 90% атак на разных сидах, а без защит уровень проигрывается.

При изменении цифр движка запускайте `pnpm test`.
